A tutor that finds the wrong rule behind your wrong answer.

Most learners aren’t missing facts. One wrong rule in their head keeps producing the same kind of mistake. Rootcause, a percentages tutor, finds that rule and helps fix it.

Perceptron Hackathon 2026, Theme 5: AI That Teaches, Problem 8

Scroll to follow the idea.

Saying “wrong” doesn’t help

Most apps mark an answer wrong and hand you more questions. But many different wrong answers can come from the same hidden rule, so more practice changes nothing.

Example: a price goes up 20%, then down 20%. A student says it ends where it started. They are adding the two changes instead of chaining them.

Five common mistakes, written as small Python rules

  1. Wrong base. Price goes from 50 to 60, and the student divides the rise by 60 (new value) instead of 50. Answer: 16.7% instead of 20%.
  2. Additive successive changes. Up 20% then down 20% gives “0% change”. The truth is 100 → 120 → 96, which is −4%.
  3. Wrong inverse. A sale price of 150 after 25% off. The student adds 25% of 150 and gets 187.5. The real original price is 150 ÷ 0.75 = 200.
  4. Percentage-points confusion. A rate moves from 10% to 12% and the student says “up 2%”. It is up 2 points, which is a 20% relative rise.
  5. Part:part read as part:whole. Boys to girls is 2:3 and the student says boys are 2/3 of the class. It is 2/5 = 40%.

Step 1: try every rule on the answer

The student enters a number, picks the method they used and rates their confidence from 1 to 5.

Python runs all five rules on the problem. Only the rules that reproduce the student’s exact answer stay lit. One answer alone gives a diagnosis of suspected, never more.

Step 2: a second problem confirms it

Code picks a second problem where the correct answer and every rule’s answer all differ, so each answer points to exactly one cause.

  1. Same rule explains both wrong answers: confirmed.
  2. Second answer is correct: a possible slip, not a misconception.
  3. Anything else: uncertain. We say so instead of guessing.

Extra: how sure are you?

Next to the method dropdown, we ask “How confident are you in this answer? (1 to 5)”. This adds a layer of metacognition.

  1. Wrong with confidence 5 flags a strong bug, a deeply ingrained rule that gets practice first.
  2. Wrong with confidence 1 hints at a careless slip, so the second problem checks it before anything is labelled.

Confidence is only a supporting signal and never decides the diagnosis. We also test whether it predicts which diagnoses the second problem confirms.

Step 3: show them why it breaks

On the student’s own numbers, we show the wrong and right methods side by side. Take 500, up 20% then down 20%:

Wrong: +20% − 20% = 0%, so 500.
Right: 500 × 1.2 = 600, then 600 × 0.8 = 480.

A short hint follows, then a fresh follow-up problem with a verified answer checks that it stuck.

Why this is different

  1. Python decides. All the maths and every diagnosis come from code. An optional LLM only turns typed working into a matching rule and rewrites our fixed explanations in friendlier words.
  2. It admits doubt. Suspected, confirmed or uncertain, never a forced label.
  3. It remembers. Every attempt is stored, so mistakes are tracked across sessions.

How we will prove it works

On peer-written wrong answers, we compare the tutor against a zero-shot LLM baseline and measure:

  1. Accuracy, and F1 for each of the five mistakes.
  2. Agreement between human labellers, and wrongly forced diagnoses.
  3. Follow-up success rate, and whether confidence predicts which diagnoses get confirmed.
  4. Error rate before and after targeted practice, against random practice.

The pilot is small, so we report trends only.

What we deliver for Problem 8

The must-haves

  1. Sort a wrong answer into one of five clear categories: wrong base, additive successive changes, wrong inverse, percentage-points confusion and part:part as part:whole.
  2. Make a new practice problem aimed at that category, with the answer checked by Python.

The stretch goals

  1. Remember each student’s mistakes across sessions.
  2. Show that targeted practice reduces the mistake more than random practice.

Plus our extra: confidence self-assessment.

Stretch goals: how we will do it

  1. Remembering across sessions. A small SQLite table logs every attempt: student, session, problem, answer, method, confidence, which rules matched and the label. A summary query gives each student’s mistake counts per rule.
  2. Targeted vs random practice. Each peer takes a pre-test, then code assigns them by coin flip to targeted problems (aimed at their confirmed rule) or random problems. A matched post-test gives the error rate before and after.
  3. Peer-written answers. Friends write wrong answers and say why. Two people label them blind, we compute their agreement, then compare tutor and zero-shot LLM against those labels.
  4. Follow-up and confidence. We log whether each follow-up is solved, and compare confirmation rates across confidence 1 to 5.

Early evidence (simulated)

We simulated 120 learners, each with one hidden bug. The tutor’s own pre-test, second problem and confirmation picked their target rule. Half then did targeted practice and half did random practice, with the same explanations in both.

Share of relevant problems answered with the target mistake. Targeted fell from 0.86 to 0.09 and random from 0.91 to 0.25, a difference in mean drop of +0.13 (95% bootstrap +0.04 to +0.22).

  1. Null check: with learning switched off, neither arm moved.
  2. Pilot size: in 200 simulated pilots of 8 learners per arm, targeted came out ahead in 185.

This is a simulation. It tests our pipeline, and the learning rate is our assumption, so it is not evidence about real students. The real answer comes from the peer pilot, and we report trends only.

Built with Antigravity

Five small jobs, one agent each, each with a check that says it works:

  1. The five rules and an answer checker
  2. The second-problem picker (all answers differ)
  3. Diagnosis labels and confidence logic
  4. Storage and the evaluation scripts
  5. The app, with method dropdown and confidence rating

Free open tools: Python, SQLite, Gradio, and Gemma 3 as the optional wording helper.
